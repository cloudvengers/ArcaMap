# API 서버 용량과 부하 대응 — 기존 사양·목표값 유지 및 ASG 최소 1대·최대 2대

## 배경과 문제

### 배경

- 현재 AWS에 서비스 인프라는 배포되어 있지 않으며, 고가용성 구성을 단일 구성 운영 기반으로 재구성합니다.
- 기존 API 서버는 EC2 `t3.small`, 암호화된 gp3 루트 볼륨 20GiB를 사용하며, ASG 최소 2대·최대 4대와 CPU·메모리 목표 추적 정책을 구성하고 있습니다.
- ASG(Auto Scaling Group)는 EC2 인스턴스 수를 유지하고 부하에 따라 증설·축소하는 그룹입니다.
- API 서버는 프라이빗 서브넷에 배치하고, 성능 효율성·지속 가능성·비용 최적화를 고려해 기본 운영 용량과 부하 대응 범위를 정해야 합니다.

### 문제

- 기존 ASG의 최소 2대는 서버 1대를 기본으로 운영하려는 이번 재구성 방향과 맞지 않습니다.
- 기본 운영 대수를 줄이면서도 부하 증가에 대응할 수 있도록 ASG의 자동 증설·축소 기능을 유지해야 합니다.
- 이번 용량 조정에서는 기존 EC2 사양과 CPU·메모리 목표값을 유지해야 합니다.

## 검토한 대안

- **기존 ASG 최소 2대·최대 4대 유지:** EC2 사양과 목표 추적 정책을 유지하며 더 많은 처리 용량을 확보하지만, 최소 2대의 실행 비용을 부담합니다.
- **ASG 최소 1대·최대 2대로 조정:** 같은 EC2 사양과 목표 추적 정책으로 기본 운영 용량을 줄이고, 부하 증가 시 최대 2대까지 자동 증설합니다. 기존 구성보다 처리 용량의 상한이 낮아집니다.

## 결정과 이유

**선택: EC2 사양과 CPU·메모리 목표값을 유지하고, ASG를 최소 1대·최대 2대로 운영**

- EC2 인스턴스 유형은 `t3.small`, 루트 볼륨은 암호화된 gp3 20GiB를 유지합니다.
- ASG는 기본 1대로 운영하고, 부하 증가 시 최대 2대로 증설합니다. 부하 대응을 위한 최소 대수는 1대, 최대 대수는 2대로 설정합니다.
- CPU 목표 추적 정책은 ASG 평균 CPU 사용률인 `ASGAverageCPUUtilization`의 목표값 50%를 유지합니다.
- 메모리 목표 추적 정책은 CloudWatch Agent가 수집하는 `CWAgent / mem_used_percent`를 사용하며, `AutoScalingGroupName` 차원의 `Average` 통계와 목표값 50%를 유지합니다.
- 두 목표 추적 정책 모두 축소를 허용합니다. 어느 하나가 증설을 요구하면 최대 2대 범위에서 증설하고, 두 정책이 모두 축소 조건을 충족하면 최소 1대 범위에서 축소합니다. 나머지 기존 정책 설정도 유지합니다. [AWS 목표 추적 정책](https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-scaling-target-tracking.html)
- AMI 업데이트 시 인스턴스를 교체하는 Instance Refresh는 기존 최소 정상 비율 100%·최대 정상 비율 200%를 유지합니다. 두 비율은 ASG의 목표 용량을 기준으로 계산하며, 새 서버의 상태 검사와 워밍업이 완료된 뒤 기존 서버를 종료합니다. [AWS Instance Refresh 동작](https://docs.aws.amazon.com/autoscaling/ec2/userguide/instance-refresh-overview.html)
- 기본 1대 운영 상태에서 AMI를 교체하면 기존 1대와 새 1대가 잠시 함께 실행되어 최대 2대가 됩니다. 부하 증가로 이미 2대로 증설된 상태에서 AMI를 교체하면 기존 2대와 새 2대가 잠시 함께 실행되어 최대 4대가 될 수 있습니다. 교체가 끝나면 해당 목표 용량인 1대 또는 2대로 돌아갑니다.
- 최소 운영 대수를 줄여 상시 유지하는 서버 용량과 비용을 낮추고, ASG로 부하 증가에 대응합니다.

### 결과

- 이점: ASG 최소 대수를 2대에서 1대로 줄여 기본 운영 시 EC2 실행 비용과 유휴 용량을 줄일 수 있습니다.
- 이점: 기존 CPU·메모리 목표 추적 정책을 유지해 부하에 따라 최대 2대까지 자동 증설할 수 있습니다.
- 제약: 서버 1대로 운영하는 동안 해당 서버에 장애가 발생하면 요청을 처리할 서버가 없어 복구까지 서비스가 중단될 수 있습니다.
- 제약: AMI 교체 중 기존 서버와 새 서버를 함께 실행하는 동안 임시 추가 용량에 대한 비용이 발생합니다.
- 제약: 부하에 따른 자동 증설은 최대 2대까지이며, 그 이상의 처리 용량이 필요하면 사양이나 ASG 대수 범위를 다시 결정해야 합니다.
- 제약: 메모리 목표 추적은 부하가 분산되어 인스턴스당 평균 메모리 사용률이 낮아지는 경우에 적합합니다. 서버마다 발생하는 고정 메모리 점유나 메모리 누수는 증설만으로 해결되지 않습니다. [AWS 메모리 기반 목표 추적](https://aws.amazon.com/blogs/mt/create-amazon-ec2-auto-scaling-policy-memory-utilization-metric-linux/)
- 제약: CPU·메모리 목표값 50%는 기존 설정을 유지한 값이며, 재구성한 서비스에 적합한지는 향후 운영으로 판단합니다.
