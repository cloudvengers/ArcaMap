# S3 저장소 운영 — HTTPS 접근 강제·백업 대상 버킷 버전 관리·이전 버전과 미완료 업로드 7일 정리

## 배경과 문제

### 배경

- 현재 AWS에 서비스 인프라는 배포되어 있지 않으며, 성능 효율성·지속 가능성·비용 최적화·보안을 고려한 단일 구성 운영 기반으로 재구성합니다.
- S3는 웹 정적 파일, 사진, 지도 데이터, CloudFront 접근 로그, API 배포 파일을 용도별 버킷에 저장합니다. 웹 정적 파일은 HTML·JS·CSS·아이콘·지도 실행용 워커이며, 실제 지도 데이터인 PMTiles는 별도 지도 버킷에 저장합니다.
- 콘텐츠는 지정 CloudFront 배포가 읽고, API 배포 파일은 Image Builder가 읽습니다. 기존 지도 버킷은 연결해 사용하며 새로 생성하지 않습니다.

### 문제

- HTTP 요청을 거부하는 버킷 정책은 API 배포 버킷에만 있습니다. 웹·사진·지도·로그 버킷에도 전송 보안을 명시적으로 적용해야 합니다.
- 웹 정적 파일 버킷은 버전 관리가 비활성화되어 있습니다. 같은 경로의 HTML을 덮어쓰거나 객체를 삭제하면 S3에 저장된 이전 버전으로 복원할 수 없습니다.
- 사진 버킷은 버전 관리와 이전 버전 7일 보존을 사용합니다. AWS Backup 대상으로 정한 웹·사진·지도·CloudFront 접근 로그·API 배포 버킷 모두에 버전 관리와 이전 버전 정리 기준이 필요합니다.
- 로그 버킷에 버전 관리를 활성화하면 현재 객체 30일 만료 후에도 데이터가 이전 버전으로 남습니다. 영구 삭제를 위한 이전 버전 만료 규칙이 필요합니다.
- 파일을 여러 조각으로 나누어 올리는 멀티파트 업로드의 미완료 조각 정리 규칙이 없습니다. 완료하거나 중단하지 않은 업로드 조각은 저장 비용이 발생하며, 일반 객체 만료 정책과 구분해 정리해야 합니다. [AWS 멀티파트 업로드 비용과 중단](https://docs.aws.amazon.com/cli/latest/reference/s3api/create-multipart-upload.html)

## 검토한 대안

| 항목 | 기존 방식 유지 | 변경안 |
| --- | --- | --- |
| 전송 보안 | API 배포 버킷에만 HTTP 거부 적용 | 모든 서비스 버킷에 HTTPS 접근을 강제하고 AWS 서비스 호출에 맞는 조건 적용 |
| 버전 관리·복원 | 사진의 이전 버전 7일 보존을 유지하고 웹은 원본 파일을 준비해 재배포 | 모든 백업 대상 버킷에 버전 관리를 활성화하고 이전 버전 7일 보존·정리 |
| 미완료 업로드 | 필요할 때 수동 정리 | 업로드 시작 후 7일이 지나도 미완료인 업로드를 자동 중단·정리 |

## 결정과 이유

**선택: 모든 서비스 버킷에 HTTPS 접근을 강제하고, 모든 백업 대상 버킷의 버전 관리와 이전 버전 7일 보존을 적용하며, 미완료 업로드를 시작 후 7일 기준으로 자동 정리**

- 콘텐츠·로그·배포 파일의 전송 보안 기준을 통일하고 기존 CloudFront·로그 전달·Image Builder 접근을 유지합니다.
- 모든 백업 대상 버킷에 AWS Backup의 필수 조건인 버전 관리를 활성화하고, 덮어쓰기·삭제 전의 내용을 원본 버킷에서도 복원할 수 있도록 합니다.
- 원본 이전 버전의 보존 기간도 백업 정책과 같은 7일로 맞춰 복원 이력을 확보하면서 저장량 누적을 제한합니다. AWS Backup 복구 지점은 생성 시점부터, S3 이전 버전은 이전 버전이 된 시점부터 각각 7일을 계산하며 별도 규칙으로 관리합니다.
- 미완료 업로드의 조각을 자동 정리해 반복적인 수동 작업과 불필요한 저장량·비용을 줄입니다.

### HTTPS 접근 강제

- 적용 대상은 웹 정적 파일·사진·지도·CloudFront 접근 로그·API 배포 버킷입니다. 각 버킷과 해당 버킷의 객체 ARN 범위에 `s3:*` 명시적 거부 정책을 적용합니다.
- 거부 조건은 `aws:SecureTransport=false`와 `aws:PrincipalIsAWSService=false`를 함께 사용합니다. 일반 주체의 HTTP 요청을 거부하면서, 네트워크 정보가 생략되는 AWS 서비스 간 호출을 잘못 차단하지 않도록 합니다. [AWS 전송 보안과 서비스 주체 조건](https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html)
- AWS 서비스 주체를 위 거부 조건에서 제외하는 것은 새로운 읽기·쓰기 권한을 부여하는 것이 아닙니다. 기존 CloudFront 배포 ARN 조건, 로그 전달의 계정·소스 ARN 조건, Image Builder의 지정 객체 읽기 권한을 유지합니다.
- 기존 콘텐츠 읽기·로그 쓰기 허용과 HTTPS 거부를 같은 버킷 정책에 구성해 기존 허용 정책을 덮어쓰지 않도록 합니다.

### 백업 대상 버킷 버전 관리와 원본 정리

- AWS Backup 대상인 웹 정적 파일·사진·지도·CloudFront 접근 로그·API 배포 버킷 모두에서 버전 관리를 활성화합니다. 버전 관리는 버킷 전체에 적용되며, 현재 객체의 정상 콘텐츠 제공은 유지합니다. 버전 관리와 원본 수명주기는 해당 버킷을 관리하는 환경·모듈에서 설정합니다. [AWS S3 백업 필수 조건](https://docs.aws.amazon.com/AmazonS3/latest/userguide/backup-for-s3.html), [AWS S3 버전 관리](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

| 대상 | 현재 객체 보존·만료 | 이전 버전 만료 |
| --- | --- | --- |
| 웹 정적 파일·사진 | 현재 객체 만료 규칙 없음 | 이전 버전이 된 시점부터 7일 |
| 지도·API 배포 파일 | 기존 현재 객체 보존 방식 유지 | 이전 버전이 된 시점부터 7일 |
| CloudFront 접근 로그 | 생성 후 30일 만료 | 이전 버전이 된 시점부터 7일 |

- 모든 대상 버킷에 `NoncurrentVersionExpiration.NoncurrentDays=7`을 적용합니다. 사진의 기존 7일 기준을 유지하고 웹·지도·로그·API 배포 버킷에도 같은 기준을 적용합니다.
- 삭제 마커는 객체가 삭제된 상태임을 나타내는 표식입니다. 이전 데이터 버전이 모두 제거되고 삭제 마커만 남으면 만료 삭제 마커로 정리합니다. [AWS 버전별 삭제와 수명주기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html)
- 로그의 현재 객체가 30일 만료되면 삭제 마커가 추가되고 데이터는 이전 버전으로 전환됩니다. 그 시점부터 7일이 지나면 영구 삭제 대상이 됩니다. [AWS 버전 관리 버킷의 만료 동작](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html)
- HTML 덮어쓰기 복원은 보존된 이전 버전을 같은 객체 경로의 현재 버전으로 복사하는 방식으로 수행합니다. 버전 ID를 지정하지 않은 삭제로 생성된 삭제 마커는 해당 마커의 버전 ID를 지정해 제거하면 보존된 객체를 다시 제공할 수 있습니다. [AWS 이전 버전 복원](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RestoringPreviousVersions.html)
- 내용 변경 시 해시 자산의 파일명이 바뀌는 배포 방식은 유지합니다. 이전 버전 7일 만료는 같은 객체 경로의 과거 버전에 적용되며, 과거 배포의 해시 파일이 별도 경로의 현재 객체로 남아 있는 경우에는 적용되지 않습니다.
- 버전별로 전체 객체 저장 비용이 발생하므로 이전 버전 만료 정책을 함께 적용합니다. [AWS 버전별 저장 비용](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html), [AWS S3 요금](https://aws.amazon.com/s3/pricing/)

### 미완료 멀티파트 업로드 정리

- 웹 정적 파일·사진·지도·CloudFront 접근 로그·API 배포 버킷에 `AbortIncompleteMultipartUpload`를 적용하고 `DaysAfterInitiation=7`로 설정합니다.
- 업로드 시작 후 7일이 지나도 완료되지 않은 업로드를 자동 중단하고 관련 조각을 삭제합니다. 완료된 업로드와 저장된 객체에는 적용하지 않습니다. AWS는 비용 최소화를 위한 정리 규칙을 권장하며 7일 설정 예시를 제공합니다. [AWS 미완료 업로드 정리](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html)
- 각 버킷의 이전 버전·삭제 마커 정리와 로그 현재 객체 만료 규칙에 이 정리 규칙을 함께 구성합니다. 기존 지도 버킷의 수명주기 설정도 기존 규칙을 유지하면서 새 규칙을 통합합니다.
- 7일은 정상 업로드에 여유를 두면서 장기간 미완료인 조각의 누적을 제한하기 위한 운영 값입니다.

### 결과

- 이점: 서비스 버킷의 일반 주체 접근에 HTTPS를 강제하면서 기존 AWS 서비스 연결을 유지할 수 있습니다.
- 이점: 모든 대상 버킷이 AWS Backup의 버전 관리 조건을 충족하며, 덮어쓰기·오삭제 후 원본에 보존된 이전 버전도 복원에 활용할 수 있습니다.
- 이점: 미완료 업로드의 조각을 자동 정리해 불필요한 저장 비용과 수동 정리 부담을 줄입니다.
- 제약: 원본 이전 버전의 저장·복원 요청 비용이 발생합니다. 로그는 현재 객체 30일 만료 후에도 이전 버전 7일 보존에 따른 저장 비용이 발생합니다.
- 제약: 버전 관리를 활성화한 버킷은 버전 관리 미사용 상태로 되돌릴 수 없으며 일시 중단만 가능합니다.
- 제약: 원본 버킷에서 이전 버전이 영구 삭제되면 S3 버전 관리로는 복원할 수 없습니다. AWS Backup을 통한 복원은 해당 복구 지점의 내용과 보존 상태에 따라 별도로 판단합니다.
- 제약: 수명주기 만료는 UTC 기준 일 단위로 평가하고 삭제는 비동기로 처리합니다. 설정한 일수가 지난 시점과 실제 삭제 시점은 같지 않을 수 있습니다. [AWS 수명주기 처리 시점](https://repost.aws/knowledge-center/s3-lifecycle-rule-delay)
- 제약: 시작 후 7일이 지나도록 완료하지 못한 업로드는 자동 중단 대상이 되므로 다시 시작해야 할 수 있습니다.
