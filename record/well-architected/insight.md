## 1. 종합 인사이트

### 1.1 자원 크기를 결정하려면 업무별 부하와 메모리를 함께 측정해야 합니다

**적용 모범 사례:** PERF02-BP04 「컴퓨팅 자원 구성 및 적정 크기 선정」 — 성능 요구와 CPU·메모리 등의 사용량에 맞춰 자원을 선택하고 변경 전 시험합니다.

**근거:** API 로그는 journald를 통해 수집됐지만 EC2 메모리·파일시스템 지표는 없었고, CPU 수집 간격은 5분인 반면 자동 확장 경보의 평가 간격은 1분이었습니다.

CPU만으로는 메모리 사용과 동시 요청 처리에 필요한 용량을 판단하기 어렵습니다. 별도 모니터링 시스템을 도입할 때 기존 API 로그를 활용해 검색·시설 상세 조회의 성공률·지연·동시 처리량을 메모리·CPU·DB 호출과 함께 측정하면 자원 크기의 판단 기준을 마련할 수 있습니다.

자동 확장은 부하 증가부터 새 인스턴스가 요청을 처리하기까지 걸리는 시간으로 평가해야 합니다. 대표 부하와 한 가용 영역만 남은 조건에서 성능을 확인한 뒤 인스턴스 크기·수집 간격·확장 목표를 조정합니다. 계측 범위가 넓어지면 저장·처리 비용도 늘어나므로 용량 판단에 필요한 항목부터 추가하는 것이 적절합니다.

### 1.2 비용 절감은 가용성 유지비와 데이터 처리료를 구분해야 합니다

**적용 모범 사례:** COST05-BP03 「구성 요소별 상세 분석」 — 자원 요금과 운영·관리 비용을 함께 계산하고, 예상 편익에 비례해 분석·변경 노력을 배분합니다.

**근거:** 7일 추정액 79.02달러 중 RDS 35.33달러와 NAT 두 개의 유지비 19.82달러가 합계 69.79%였으며, NAT 데이터 처리료는 0.09달러였습니다.

RDS Multi-AZ와 가용 영역별 NAT는 단일 가용 영역 장애에 대비한 구성입니다. 이중화를 줄이는 변경은 장애 대응 조건까지 바꾸므로, 비용 검토는 필요한 업무 부하를 확인한 뒤 RDS·API의 크기를 조정하는 데서 시작하는 것이 적절합니다.

S3 통신의 NAT 우회는 목적지별 이용량이 확인될 때 검토할 수 있습니다. NAT를 계속 운영하면 유지비는 그대로 발생하므로, 경로 변경으로 줄일 수 있는 소액의 처리료와 설정·운영 부담을 비교해야 합니다.

### 1.3 WAF의 탐지 목적과 공개 진입점별 보호 범위를 맞춰야 합니다

**적용 모범 사례:** SEC05-BP03 「검사 기반 보호 구현」 — 요청의 내용·위협 정보·정상 동작을 기준으로 검사 지점과 허용·거부 규칙을 정합니다.

**근거:** CloudFront WAF는 9월 15일 도입 때부터 관리형 규칙 그룹 4개를 Count로 운용했고 API ALB에는 연결되지 않았으며, 7일 WAF 비용 6.06달러 중 Anti-DDoS 규칙 비용은 4.18달러였습니다.

Count는 위협 규칙에 일치하는 요청을 관측하는 운용 방식입니다. 정적 콘텐츠의 요청을 검사하는 CloudFront WAF와 별도로, API는 ALB로 직접 들어오므로 공개 진입점마다 탐지·차단할 대상을 정해야 합니다.

규칙 일치 요청에서 정상 사용과 오탐을 구분하고, 차단이 필요한 규칙만 적용 범위와 되돌림 조건을 정해 전환하는 방향이 적절합니다. 유료 규칙의 유지 여부는 조사·대응에 활용한 결과와 비용을 함께 평가합니다. 보호 범위를 강화할 때도 정상 API와 지도 범위 요청이 계속 처리되어야 합니다.

### 1.4 사람의 상시 관리자 권한을 필요한 작업 범위로 줄일 수 있습니다

**적용 모범 사례:** SEC03-BP02 「최소 권한 부여」 — 수행할 작업·대상 자원·접근 조건에 필요한 권한만 부여하고, 일시적인 관리 권한은 작업 종료 후 회수합니다.

**근거:** API·이미지 빌드 역할은 분리되어 지정 Secret·배포 객체에 접근했지만, MFA가 등록된 IAM 사용자 한 명에게는 `AdministratorAccess`가 직접 부여되어 있었습니다.

MFA가 인증을 보호하더라도 관리자 권한으로 가능한 변경 범위는 그대로입니다. 일상적인 조회·배포·운영에는 필요한 권한을 부여하고, 관리·비상 작업에는 작업 동안 사용할 임시 권한을 구분하면 실수나 인증정보 오용의 영향을 제한할 수 있습니다.

권한을 과도하게 제한하면 Terraform 변경·이미지 빌드·Secret 조회·비상 복구가 막힐 수 있으므로 실제 작업 범위를 먼저 확인해야 합니다.

### 1.5 이미지 기능 시험에 설치 파일의 공급자 검증을 보완할 수 있습니다

**적용 모범 사례:** SEC06-BP04 「소프트웨어 무결성 검증」 — 신뢰할 수 있는 공급원의 산출물을 사용하고 암호학적 서명으로 출처와 무결성을 확인합니다.

**근거:** 이미지 빌드에는 API·DB 응답, 비루트 실행, 인증정보 보관과 로그 전달 시험이 있었지만 AWS CLI·CloudWatch Agent 설치 단계에는 공급자 서명 검증이 없었습니다.

기존 기능 시험은 실행 환경의 동작을 확인합니다. 설치 파일의 공급자 서명을 확인하면 다운로드한 파일의 출처와 무결성도 검증할 수 있습니다. 기존 빌드 단계에 공급자가 제공하는 검증 자료와 신뢰할 키의 확인 절차를 연결하는 방향이 적절합니다.

검증 실패 시 이미지 생성을 중단하고 이전 AMI로 복귀할 수 있어야 합니다. 공급자별 검증 방식과 키 갱신을 관리하는 작업이 추가됩니다.

### 1.6 데이터 복구와 보안 조사 목적에 맞춰 보존 기간을 정해야 합니다

**적용 모범 사례:** REL09-BP04 「정기적인 데이터 복구 검증」 · SEC07-BP04 「데이터 수명 주기 관리」 — 복원 시험으로 RTO·RPO와 데이터 정합성을 검증하고 데이터의 분류·접근·감사 요구에 맞춰 보존·삭제 기준을 정합니다.

**근거:** 9월 22일 구성에서 RDS 자동 백업 3일·자동 스냅샷 4개, 사진 이전 버전 7일·서비스 로그 30일·WAF 로그 14일 보존이 확인됐으며, 업무 복원 시험 결과와 복구 목표는 미확인입니다.

백업 보존 기간은 허용 복구 시간(RTO)과 허용 데이터 손실(RPO)에 맞춰 판단해야 합니다. 선택한 백업을 복원해 API 기능·데이터 정합성·소요 시간을 확인하고, 웹·지도·배포 파일은 원본 재생성과 이전 버전 복구 중 실제 사용할 경로를 정하는 것이 우선입니다.

로그는 조사에 필요한 사건과 조회 기간을 기준으로 보존합니다. 당시 CloudTrail에는 90일 관리 이벤트 이력이 있었지만 별도 Trail·Event Data Store·VPC Flow Logs는 없어 장기 관리 이력과 네트워크 흐름을 조사할 범위가 제한됐습니다. 추가 보존·수집은 필요한 조사 범위를 충족하는 수준으로 정하고 저장 비용과 민감정보 접근 통제를 함께 고려해야 합니다.

### 1.7 지도 캐시의 재사용과 웹 콘텐츠의 최신성을 함께 유지해야 합니다

**적용 모범 사례:** PERF03-BP05 「캐시를 활용하는 데이터 접근 패턴 구현」 — 접근 패턴에 맞는 캐시를 선택하고 TTL·무효화 정책으로 데이터 최신성과 원본 부하의 균형을 맞춥니다.

**근거:** 9월 14~21일 지도 파일의 HTTP 206 범위 응답은 4,401건이었으며, 정적 파일의 캐시 유효 시간(TTL) 상한은 300초였고 객체별 캐시 헤더·갱신 이력은 미확인입니다.

지도는 필요한 파일 범위만 요청하고 CloudFront 캐시에서 재사용하는 구조입니다. 이 동작을 유지하면서 홈 HTML의 갱신 주기와 버전이 고정된 자산의 재사용 조건을 구분하면 콘텐츠별 캐시 정책을 판단할 수 있습니다.

TTL을 늘리면 원본 접근을 줄일 수 있지만 변경 반영이 늦어질 수 있습니다. 조정 여부는 객체의 `Cache-Control`과 갱신 요구를 먼저 확인한 뒤 결정하고, 같은 경로·요청 범위에서 지도 응답·화면 최신성·원본 전송량을 비교해야 합니다.

## 2. 우선순위와 검증 조건

상시 권한과 설치 경로의 보호 범위를 먼저 보완하고, 자원·복구·WAF·캐시는 필요한 업무·보호 수준을 확인한 뒤 조정합니다.

| 순서 | 대상 | 선행 조건·작업 부담 | 검증 조건 |
|---|---|---|---|
| 1 | 일상·관리 권한 구분 | 필수 작업 목록과 임시 관리 권한 경로를 정해야 합니다. | 배포·복구는 가능하고 불필요한 관리 작업은 거부되며 임시 권한이 종료됩니다. |
| 2 | 설치 파일의 공급자 검증 | 공급자별 검증 방식과 키 갱신 관리가 필요합니다. | 정상 파일은 이미지 시험을 통과하고 검증 실패 파일은 설치·배포가 중단됩니다. |
| 3 | 업무·자원 측정 | 예정된 모니터링 시스템의 계측 범위와 대표 부하를 정해야 합니다. | 기능별 성공률·지연과 자원 사용을 연결하고 부하 증가·가용 영역 장애 조건의 처리 용량을 확인합니다. |
| 4 | 복구·보존 정책 | RTO·RPO와 조사 범위를 정하고 분리된 복원 시험 환경을 준비해야 합니다. | 복원한 데이터·API가 정합성 조건을 충족하고 복구 시간·손실 범위가 목표 이내입니다. |
| 5 | WAF 적용 범위 | 진입점별 위협·정상 요청·오탐 분석이 필요합니다. | 선택한 탐지·차단 목표를 충족하며 정상 요청과 오탐 시 복귀가 확인됩니다. |
| 6 | 자원 크기·NAT 경로 | 업무·장애 시 용량과 목적지별 통신을 확인해야 합니다. | 두 가용 영역의 장애 대응 조건과 요구 성능을 유지하면서 동일 업무량의 비용이 감소합니다. |
| 7 | 콘텐츠별 캐시 | 객체별 헤더와 갱신 요구를 확인해야 합니다. | 지도 범위 응답·화면 최신성을 유지하면서 원본 접근 또는 응답 지연이 감소합니다. |
