# AWS Well-Architected 인사이트 분석 가이드

## 1. 목적과 작업 범위

실제 AWS 운영을 Well-Architected Framework에 따라 분석하여 현재 상태의 적절성, 판단 근거, 서비스 영향과 개선 방향을 설명합니다. 기둥별 분석을 종합한 뒤 결정된 개선의 수행·검증 결과를 기록합니다.

- 프로젝트 및 IaC 위치: `/root/arcamap`
- 분석 문서 위치: `/root/arcamap/record/well-architected`
- 주된 분석 대상: 실제 AWS 리소스의 구성·상태·운영 지표와 해당 기둥에 필요한 운영 정보
- 주된 근거: 실제 AWS 리소스의 설정과 로그·지표·이벤트·비용 내역
- 보조 근거: 프로젝트의 IaC 및 필요한 코드·설정
- 서비스·계정·리전·리소스 범위: 분석 시작 후 실제 리소스와 IaC를 확인하여 식별

기존 문서의 조사 대상과 확인 경로를 참고하되, 수치·판정·결론을 그대로 승계하지 않고 재조회한 근거로 새로 작성합니다.

## 4. 기둥별 문서의 공통 목차

6개 기둥 문서는 아래 제목·번호·순서를 동일하게 사용합니다. 2번 제목은 해당 기둥의 공식 문서, 3번 제목은 해당 기둥의 공식 질문·BP 부록에 링크를 연결합니다. `insight.md`와 `final.md`는 역할에 맞는 별도 목차를 사용합니다.

| 본문 제목 | 작성할 내용 |
|---|---|
| `## 1. Current Operations(현재 운영 현황)` | 서비스·환경, AWS 계정·리전, 구성 확인 시점을 밝히고 아래 세 항목으로 운영 현황을 설명합니다. |
| `### 1.1 리소스 구성` | 리소스의 역할·설정·연결 관계와 대응하는 Terraform 정의 위치를 기록합니다. |
| `### 1.2 옵저빌리티 구성` | 관측 대상·목표·도구·수집 경로·경보·대시보드 설정을 설명합니다. 정의되지 않았거나 확인할 수 없는 설정은 그 상태를 명시합니다. |
| `### 1.3 텔레메트리 수집 현황` | 실제 수집 중인 로그·지표·추적·이벤트의 종류·대상·범위·확인 위치를 설명합니다. 개별 사건, 지표 관측값과 상세 분석은 4번에 둡니다. |
| `## 2. Pillar Principles(기둥의 원칙에 따른 검토)` | 공식 정의·설계 원칙을 현재 구성에 대조하여 충족·부족·확인 필요 사항을 설명합니다. 개별 BP 판정과 사건 기록은 반복하지 않고 3·4번을 참조합니다. |
| `## 3. Questions and Best Practices(질문 및 모범 사례별 상세 점검)` | 모든 공식 질문·BP를 질문별로 점검하고 판정과 사유를 남깁니다. 해당 없음·확인 불가도 생략하지 않습니다. |
| `## 4. Findings and Insights(발견 사항 및 인사이트)` | 구성·운영 현상·사건을 실제 근거로 분석하고 관련 질문·BP에 연결합니다. 상세 기록 항목은 아래 기준을 따릅니다. |
| `## 5. Conclusion(결론)` | 현재 운영 수준, 우선 검토할 개선 과제, 추가 근거와 그 부족이 판단에 미치는 영향을 요약합니다. |

질문별 항목은 `### 3.1 …`, 발견 사항별 항목은 `### 4.1 …`처럼 번호와 한국어 제목을 붙입니다. 발견 사항의 제목은 운영 대상과 핵심 현상을 드러내며 제목·번호를 문서 안에서 일관되게 사용합니다.

**BP 기록 항목**은 질문 ID, 공식 BP ID·명칭·원문 링크, 점검 기준, 실제 현재 상태, 확인 근거, 판정, 판정 사유입니다. 질문 ID는 묶음 제목에 표시하고 구성 근거는 1번, 상세 기록은 4번에 직접 연결하여 반복을 줄입니다.

**발견 사항별 기록 항목**

- 대상 리소스, 구성 확인 시점 또는 관측 기간, 조회 조건과 근거 위치
- 판단에 필요한 설정·로그·지표·변경 이력. 사건을 다룰 때는 발생 시각과 경위
- 해당 기둥의 기준에서 적절하거나 부족하다고 판단한 이유
- 확인된 원인 또는 원인 가설과 서비스 영향
- 개선 방향, 기대 효과·제약과 유지해야 할 운영 조건

여러 발견 사항이 공통 원인을 가리키면 근거를 연결하여 설명합니다. 간결하게 고치더라도 판단에 필요한 사건 순서·수치·근거를 생략하지 않습니다. 같은 사건을 여러 기둥에서 다룰 때는 각 기둥의 의미를 설명하고 공통 기록은 링크로 연결합니다.

## 5. 공통 판정 및 근거 작성 기준

| 판정 | 영문 대응 | 적용 기준 |
|---|---|---|
| 충족 | Implemented | 관련 모범 사례의 요구 사항을 충족한다는 근거가 확인됨 |
| 부분 충족 | Partially Implemented | 일부 요구 사항은 충족하지만 확인된 부족한 부분이 있음 |
| 미충족 | Not Implemented | 필요한 통제나 구성이 구현되지 않았거나 기준을 충족하지 못한다는 근거가 확인됨 |
| 해당 없음 | Not Applicable | 해당 워크로드에 적용되지 않으며 그 이유를 설명할 수 있음 |
| 확인 불가 | Cannot Determine | 조회 권한·지표·운영 기록 등의 근거가 부족하여 판단할 수 없음 |

- 조회 실패·권한 부족·자료 부재만으로 미충족이나 장애 부재를 단정하지 않습니다. 운영 절차 등 판단 근거가 부족한 항목은 확인 불가로 기록하고 필요한 자료와 판단할 수 없는 범위를 명시합니다.
- 공식 요구 사항, 관측한 사실, 분석자의 해석·가설, 기대 효과와 검증 결과를 구분합니다. 근거 없이 문제·개선 과제를 만들거나 효과를 단정하지 않습니다.
- 비밀값·인증정보는 문서에 기록하지 않습니다.

### 5.1 공통 집계 기간

- **집계 기간**: KST **2026년 9월 14일~21일 전체**, **2026-09-14 00:00:00 이상, 2026-09-22 00:00:00 미만**입니다. UTC로는 **2026-09-13 15:00:00 이상, 2026-09-21 15:00:00 미만**입니다.
- 6개 문서의 지표·로그·이벤트·비용은 이 기간으로 다시 집계하고 관련 수치·판정·해석을 갱신합니다. 기존 수치의 날짜 표기만 바꾸지 않습니다.
- 문서의 날짜·시각은 KST로 통일합니다. 특정 사건의 전후 구간은 공통 기간 안에서 따로 표시하고 비교 시 부하·구성 등 조건의 차이를 밝힙니다.
- 리소스 구성은 실제 확인 시점의 상태로 기록하고 집계 기간과 구분합니다. 현재 설정이 기간 내내 유지됐다고 가정하지 않습니다.
- 보존 범위나 원천 자료의 시간 단위로 전체 기간을 확보하지 못하면 실제 확보 범위와 판단에 미치는 영향을 밝힙니다. 다른 기간을 같은 기간의 결과로 제시하거나 누락 구간을 임의로 채우지 않습니다.

### 5.2 독자가 확인할 수 있는 근거

- 설정은 **AWS 서비스·리전·리소스 이름·설정 항목·확인 시점**, 로그는 **로그 그룹·스트림 또는 S3 경로와 기간**, 지표는 **대상 리소스·지표·기간**으로 확인 위치를 제시합니다.
- Terraform은 실제 파일과 리소스 정의 위치에 링크를 연결하고 대응하는 AWS 설정 위치를 함께 제시합니다. IaC 선언을 실제 적용 상태로 단정하지 않으며 운영 판단은 실제 AWS 조회 결과를 중심으로 내립니다.
- 도구·프로토콜 이름, 호출 과정·ID, 실행 성공 메시지로 근거를 대신하지 않습니다. 독자가 찾을 수 없는 내부 근거 번호만 단독으로 쓰지 않습니다.
- 수치는 대상·기간·단위·집계 방식과 판단에 쓰이는 의미를 설명합니다. 평균·최대·최소·합계와 필요한 관측 간격을 구분하고 자료가 없는 구간을 0으로 간주하지 않습니다.
- 지표명·리소스 ID·반환 건수·원시 수치는 대상 식별이나 판단 재현에 필요한 범위에서 사용합니다. 해당 기둥의 판단에 쓰이지 않는 정보는 제외하고 개선 판단에는 부하·다른 자원 사용·운영 요구 등 필요한 조건을 함께 검토합니다.

### 5.3 비용 최적화 분석

현재 운영 구성을 기준으로 **비용 구조·자원 사용 효율·불필요한 비용·개선 방향**을 분석합니다. 크레딧 관련 내용은 비용 최적화 문서 전체에서 삭제하고 분석·설명에서 제외합니다. 별도의 재무 전제나 가상 운영 시나리오를 덧붙이지 않습니다.

항목별 비용 발생 원인, 현재 사용량·운영 요구에 비춘 적절성, 변경 효과와 운영상 제약을 설명합니다. 고정 유지 비용과 사용량에 따른 비용을 구분하고 전송량만으로 실제 청구 금액이나 절감액을 단정하지 않습니다.

## 6. 종합 인사이트 작성 기준

`insight.md`는 6개 기둥의 분석을 종합한 의사결정 자료입니다.

- 주요 결과를 원본 기둥 문서·질문·BP에 연결하고 같은 원인이나 변경 대상의 개선 과제는 통합합니다.
- 기둥 간 영향과 상충 관계를 설명합니다.
- 영향·시급성·예상 작업 범위로 개선 우선순위를 정하고 추가 근거가 필요한 사항을 남깁니다.

## 7. 개선 결과 작성 기준

`final.md`에는 다음 내용을 기록하며 실제 수행·검증한 범위만 개선 완료로 표현합니다.

- 개선 대상 인사이트와 변경 전후의 상태·내용
- 코드·IaC 수정 여부와 실제 AWS 운영 환경 적용 여부
- 검증 방법·결과·확인된 효과와 미검증·미완료·보류 사항

## 8. 진행 및 완료 기준

1. 문서 구조와 작성 기준을 확인하고 작업 대상·범위별 계획을 작성·보고한 뒤 사용자 승인에 따라 진행합니다.
2. 실제 AWS 운영 현황과 공식 평가 기준을 확인하고 공통 기간의 자료를 집계하여 6개 기둥 문서를 작성합니다.
3. 분석 결과를 종합하여 `insight.md`에 개선 방향과 우선순위를 정리합니다.
4. 사용자와 개선 대상·적용 범위를 결정한 뒤 해당 작업을 수행합니다.
5. 실제 변경을 검증하고 `final.md`에 결과를 기록합니다.

각 단계는 합의한 범위 안에서 진행하며 완료 후 불필요한 후속 작업이나 반복 확인을 추가하지 않습니다. 분석 문서는 독자가 현재 운영 방식·실제 기록·판단 근거·영향·개선 이유를 이해할 수 있는지 검토합니다. 작업 진행·제출·검토 기록은 `plan.md`, `review-checklist.md`와 완료 보고에 남깁니다.

## 9. Document Style(문서 스타일)

문체 기준은 /root/arcamap/README.md와 /root/arcamap/terraform 아래 README의 문체·서식을 따르며 아래 규칙을 작성과 검토에 공통으로 적용합니다.

### 9.1 도입부와 문체

- 시작 순서는 **제목 → 아이콘을 포함한 굵은 한 줄 요약 → 짧은 도입 문단 → 공통 기간·구성 확인 시점 → 목차 링크**입니다. 목차 링크는 실제 제목 앵커에 연결하고 `·`로 구분합니다.
- 제목은 `# Security(보안)`처럼 영문·한글 명칭을 병기하고 파일 번호는 붙이지 않습니다. 기둥 아이콘은 **⚙️ 운영 우수성·🔒 보안·🛡️ 신뢰성·⚡ 성능 효율성·💰 비용 최적화·🌱 지속 가능성**입니다.
- 한 줄 요약과 도입부는 실제 서비스의 운영 특징과 주요 구성의 역할·연결 관계를 설명합니다. 문서 종류를 되풀이하지 않습니다.
- 독자가 ArcaMap의 동작과 운영상 의미를 이해하도록 자연스러운 한국어 존댓말을 사용합니다. 서비스·리소스·요청·운영 절차를 주어로 쓰고 현재 구성은 현재형으로, 과거 사건은 시각과 함께 과거형으로 씁니다.
- 작성 경위, 에이전트 배정·제출, 도구 실행·재시도·성공 여부, 자체 검증·완료 선언은 분석 본문에서 제외합니다. 같은 뜻을 반복하거나 “개선이 필요합니다”만으로 설명을 끝내지 않습니다.

다음은 문장 형식의 예시이며 실제 문서에는 근거를 확인한 경우에만 사용합니다.

| 작업 보고식 표현 | 운영을 설명하는 표현 |
|---|---|
| 보안 그룹을 조회하여 구성을 확인했습니다. | 보안 그룹은 ALB에서 API로 들어오는 연결을 허용합니다. |
| 경보 조회에 성공했으며 알림 설정이 없는 것을 확인했습니다. | CloudWatch 경보는 상태를 표시하지만 운영자에게 알림을 보내지는 않습니다. |

### 9.2 문단·목록·표

- **문단**은 하나의 구성·현상·판단을 다룹니다. 핵심을 먼저 밝히고 동작·근거·영향을 연결하며 원인과 영향의 설명을 잘게 나눈 목록으로 바꾸지 않습니다.
- **역할별 설명 목록**은 `- 아이콘 **항목명** — 설명` 형식으로 대상의 역할·동작·목적을 적고 항목 사이에 빈 줄을 둡니다. 역할별 아이콘은 README를 참고해 일관되게 사용하며 주요 제목·일반 문단·모든 표 셀에 붙이거나 판정을 아이콘·색상만으로 대신하지 않습니다.
- **번호 목록**은 요청 처리·배포·장애 진행처럼 순서가 있는 흐름에 사용합니다. 각 단계의 주체와 동작을 밝히고 현재 상태와 개선 제안을 섞지 않습니다. 사건의 시간 순서는 짧은 표로 정리할 수도 있으며 원인·영향 분석은 이어지는 문단에 씁니다.
- **표**는 리소스별 설정·수집 위치·기간별 수치·BP 판정처럼 같은 항목으로 비교할 때 사용합니다. 목적에 필요한 열만 두고 표 전후에 핵심 의미를 설명합니다. 긴 분석은 셀 밖으로 옮기며 BP별 설명을 붙일 때도 필수 항목과 해당 BP의 관계를 유지합니다.
- 표의 설명 열은 왼쪽 정렬하고 짧은 요약값은 가운데 정렬할 수 있습니다. 한 셀에 여러 문단·긴 목록을 넣지 않으며 `<br>`는 짧은 명칭을 나눌 때만 사용합니다.

### 9.3 표기·링크·간격

- **굵은 글씨**는 핵심 대상·동작·조건·판단에 필요한 값에, 인라인 코드는 리소스 식별자·설정 키·경로·포트·로그 필드에 사용합니다. 문단 전체나 모든 셀을 강조하지 않습니다.
- 기술 용어와 지표는 처음 나올 때 대상의 역할과 측정 의미를 설명합니다. 큰 바이트 값은 MB·GB 또는 MiB·GiB로 환산하고 십진·이진 단위를 구분합니다. 비교값의 단위·정밀도를 맞추고 불필요한 소수 자릿수는 줄입니다.
- 링크 이름은 연결 대상을 설명합니다. 저장소 파일은 문서 위치를 기준으로 실제 파일에, 외부 링크는 해당 설정이나 공식 항목에 연결합니다.
- 운영 제약은 `> **제약명**: 원인과 운영상 영향`으로 적습니다. 여러 제약을 묶는 하위 제목에만 ⚠️를 사용하고 일반 설명 전체를 인용문으로 만들지 않습니다.
- 제목 뒤와 문단·표·목록·코드 블록 앞뒤에 빈 줄을 둡니다. 문단 안에서는 문장마다 강제 줄바꿈을 넣지 않습니다.
- 그림은 관계·흐름 설명에 필요한 기존 자료를 연결하고 설명적인 대체 텍스트를 씁니다. 디렉터리 구조가 필요하면 `text` 코드 블록을 사용하며 서식을 채우기 위한 그림·코드·트리는 추가하지 않습니다.
