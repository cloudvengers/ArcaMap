# insight-2 — v1·v2 비교 인사이트

## 1. 분석 기준

- **목적:** v1에서 v2로 변경한 인프라의 운영 결과와 비용 구조를 비교합니다.
- **운영 비교:** UTC 2026-09-18 00:00~24:00(v1), 2026-10-04 00:00~24:00(v2)입니다.
- **비용 비교:** UTC 2026-09-18 00:00~24:00(v1), 2026-10-04 00:00~24:00(v2)입니다.
- **참고 자료:** [v1 인사이트](insight.md), [변경 결정 목록](../madr/madr.md), [v2 아키텍처](../architecture/v22.png)입니다.

## 2. 변경 결과와 운영 인사이트

**(2.1) RDS·NAT 상시 비용 축소로 v1 대비 일별 사용료 약 62.89% 감소**

일별 계정 사용료는 v1 **약 11.3817달러**에서 v2 **약 4.2233달러**로 **약 7.1585달러** 감소했습니다. RDS 비용 제거와 NAT 유지료 감소의 합계는 **약 6.4627달러**로, 전체 감소액의 **약 90.28%**에 해당합니다. v1에서 식별한 DB 상시 실행과 NAT 이중 구성의 비용 부담을 줄인 결과입니다.

| 주요 항목 | v1 비용(USD) | v2 비용(USD) | 변경 결과 |
| --- | ---: | ---: | --- |
| RDS | 약 5.0467 | 비용 행 없음 | Multi-AZ DB 인스턴스의 상시 실행 비용 제거 |
| NAT 유지 | 약 2.8320 | 약 1.4160 | NAT 2개에서 1개로 축소 |
| EC2 실행 | 약 1.2480 | 약 0.6038 | API 상시 2대에서 1대로 축소 |
| DSQL Endpoint 유지 | 없음 | 약 0.3120 | DB 사설 연결 비용 추가 |
| AWS Backup | 비용 행 없음 | 약 0.2278 | 공통 백업 저장 비용 추가 |
| KMS | 0.0000 | 약 0.0323 | 암호화 키 유지 비용 추가 |

**근거:** Cost Explorer의 서비스·사용 유형별 집계에서 v1 RDS 비용 약 5.0467달러가 v2에 없고, NAT 과금 시간이 48시간에서 24시간으로 줄어 유지료 약 1.4160달러가 감소했습니다.

**(2.2) NAT 2개를 NAT 1개·DSQL Endpoint 1개로 바꿔 합산 유지료 약 38.98% 절감**

v1의 NAT 2개 유지료는 **약 2.832달러**였습니다. v2는 NAT 1개에 **약 1.416달러**, DSQL Endpoint 1개에 **약 0.312달러**를 사용해 합계 **약 1.728달러**가 발생했습니다. **NAT 수량 축소로 확보한 절감액으로 DB 사설 연결을 추가하고, 두 자원의 합산 유지료를 하루 약 1.104달러 줄였습니다.**

v2의 NAT 데이터 처리료는 **약 0.0057달러**이며, NAT 유지·처리료 합계에서 유지료가 **약 99.60%**를 차지합니다. 이번 NAT 비용 감소는 유지 수량을 줄인 효과가 중심입니다.

**근거:** Cost Explorer에서 NAT 과금 시간은 v1 48시간에서 v2 24시간으로 줄고 Endpoint 24시간이 추가됐으며, 유지료 차이 2.832 − (1.416 + 0.312) = 1.104달러는 v1 대비 약 38.98%입니다.

**(2.3) API 2대 → 1대 축소, 저부하에서 정상 대상과 CPU 여유 유지**

v1은 API 2대, v2는 1대를 하루 동안 유지했습니다. v2의 CPU는 **평균 0.87%·최대 2.36%**였고, ALB 상태 검사 **5,756건**은 모두 성공했습니다. **관측된 저부하에서는 서버 수를 절반으로 줄인 뒤에도 API 가동 상태와 CPU 여유를 유지했습니다.**

**근거:** CloudWatch의 ASG 가동 대수와 ALB 정상 대상 수는 v2의 5분 구간 288개에서 모두 1대였으며, ALB 상태 검사 로그 5,756건은 전부 `PASS·200`이었습니다. [상시 1대 운영 결정](../madr/0005-api-capacity.md)

시스템 로그에서 집계한 HTTP 요청 **5,839건** 중 `/health`는 **5,756건·98.58%**이었습니다. 나머지 **83건**은 모두 404 응답이며, 장소·필터 조회 호출은 기록되지 않았습니다. 이날의 CPU·메모리 관측값은 상태 검사 중심의 기본 운영 부하를 보여 줍니다.

**근거:** `/arcamap/ec2/system`의 Uvicorn 요청 로그를 경로·응답 코드로 집계하면 `/health·200` 5,756건과 기타 경로의 404 응답 83건이며, 상태 검사 비중은 5,756 ÷ 5,839 = 98.58%입니다.

**(2.4) WAF 보호 범위를 CloudFront에서 API까지 넓히고 v1 대비 비용 약 43.23% 절감**

v1은 CloudFront 관리형 규칙을 Count로 운영했고 API ALB에는 WAF가 없었습니다. v2에서는 API WAF가 검사한 **606건 중 437건·72.11%**를 차단했고, CloudFront에서도 **56건**을 차단했습니다. API 차단에는 환경 설정 파일을 찾는 `/.env` 요청 **25건**, WordPress 관리 경로 `/wp-admin/admin-ajax.php` 요청 **3건**이 포함됐습니다. 서비스와 관계없는 경로 탐색에 차단 규칙이 실제로 적용됐습니다.

WAF 비용은 **약 0.9676달러 → 약 0.5493달러**로 감소했습니다. v1의 Anti-DDoS 유지료 **약 0.6667달러**를 제거하면서 API 보호를 추가해, **두 진입점의 요청을 차단하는 운영 결과와 비용 감소를 함께 얻었습니다.**

**근거:** API WAF 로그의 최종 `BLOCK`은 437건, CloudFront 차단 지표는 56건이며, Cost Explorer에서는 v1의 Anti-DDoS 유지료 항목이 v2에서 사라지고 WAF 총비용이 약 0.4183달러 감소했습니다. [v1의 Count 운영·API WAF 미연결 기록](well-architected/02-security.md#sec-f01)

**(2.5) v1에서 WAF 검사가 없던 API 진입점에 차단 적용, 서버 도달 전 437건 차단**

v1은 API ALB에 WAF가 없었고, v2는 WAF가 규칙에 일치한 요청 **437건**을 서버 도달 전에 차단했습니다. v2의 외부 요청 전체를 처리 단계별로 집계하면 다음과 같습니다.

| 처리 위치·결과 | 요청 수 | API 서버 전달 |
| --- | ---: | --- |
| WAF 차단·403 응답 | 437 | 없음 |
| ALB 리디렉션·301 응답 | 86 | 없음 |
| ALB의 400 응답 | 86 | 없음 |
| ALB의 460 응답 | 1 | 없음 |
| API 서버의 404 응답 | 83 | 전달됨 |
| **합계** | **693** | **83건·11.98%** |

**단일 API 서버에 도달한 외부 요청은 전체의 11.98%였습니다.** 요청 차단과 리디렉션을 진입점에서 처리하는 구성이 API 서버의 요청 처리 범위를 줄였습니다.

**근거:** ALB 접근 로그를 실행 동작과 대상 응답 코드로 묶으면 610건은 대상 응답이 없고, `forward` 동작과 대상 응답 코드가 함께 기록된 요청은 83건입니다.

**(2.6) v1의 CPU 중심 용량 판단을 CPU·메모리 실측으로 확대**

v1에서는 메모리 지표 표본이 없었습니다. v2는 하루 전체의 메모리 사용률과 가용 메모리를 수집했고, 사용률은 **평균 19.01%·최대 19.44%**, 가용 메모리는 **최소 1.333GiB**였습니다. CPU·메모리 목표 추적 기준은 각각 **50%**입니다. **단일 서버의 용량을 CPU와 메모리 양쪽의 실측값으로 판단할 수 있게 됐습니다.**

**근거:** CloudWatch Agent의 메모리 사용률·가용 메모리 지표는 각각 288개 구간에 1,440개 표본이 있으며, 가용 메모리 최솟값 1,431,617,536바이트는 약 1.333GiB입니다. [메모리 수집·목표 추적 구성](../madr/0006-cloudwatch-observability.md)

**(2.7) 경보 수동 조회에 SNS 자동 전달 추가, v1의 알림 미설정 해소**

v1의 서비스 경보 9개에는 알림 동작과 수신 대상이 없었습니다. v2는 직접 구성한 운영 경보 **8개**에 경보 발생·정상 전환·데이터 부족의 SNS 알림을 연결했습니다. 비교일 전인 **10월 3일 15:14:08(UTC)**에는 DSQL 연결 수 경보의 데이터 부족 상태가 SNS로 전달됐습니다. 경보 상태를 직접 조회하던 운영에 자동 전달 경로가 추가됐습니다.

**근거:** CloudWatch 경보 8개의 세 가지 상태 알림에 SNS가 지정돼 있으며, DSQL 연결 수 경보 이력에는 같은 시각의 `OK → INSUFFICIENT_DATA` 전환과 SNS 작업 `Succeeded`가 기록돼 있습니다. [상태별 SNS 연결 결정](../madr/0006-cloudwatch-observability.md)

**(2.8) v1에서 버전 관리가 없던 웹·지도·API 배포 파일에 7일 복구 수단 확보**

v1에서는 웹·지도·API 배포 파일의 버전 관리가 설정돼 있지 않았습니다. v2는 해당 파일의 이전 버전을 S3에 보존하고, AWS Backup에도 복구 지점을 확보했습니다.

공통 백업 볼트에는 **EC2 1개·DSQL 1개·S3 5개**의 완료된 복구 지점이 있습니다. 모두 비교일 전에 생성·완료됐으며 보존기간은 **7일**입니다. 웹·사진·지도·API 배포 파일·CloudFront 로그의 S3 버킷 5개에도 버전 관리와 이전 버전 7일 보존을 적용했습니다. **DB와 서버의 백업, 콘텐츠의 이전 버전을 함께 복구 수단으로 확보했습니다.**

AMI에는 생성 후 **7일 정리**와 보호 태그에 따른 삭제 제외 정책을 설정했습니다.

**근거:** [v1 인사이트](insight.md)의 웹·지도·API 배포 파일 버전 관리 미설정 항목에 대해, v2는 S3 버킷 5개의 이전 버전 7일 보존과 `COMPLETED·DeleteAfterDays=7`인 복구 지점 7개를 확인했습니다. [백업 관리](../madr/0010-aws-backup-management.md) · [S3 보존](../madr/0008-s3-storage-policies.md) · [AMI 정리](../madr/0009-image-builder-operations.md)

복구 범위를 확대한 v2에는 v1 비용 집계에 없던 AWS Backup 비용 **약 0.2278달러**가 추가됐으며, v2 총비용의 **약 5.39%**입니다. 해당 서비스의 비용 행에는 S3 백업 저장료 **약 0.2277625달러**, DSQL 백업 저장료 **약 0.0000006달러**가 기록됐습니다. 이번 비용 집계에서 AWS Backup 지출을 결정한 대상은 S3였습니다.

**근거:** Cost Explorer의 AWS Backup 사용 유형 중 S3 저장료를 서비스 총비용 약 0.2277631달러로 나누면 약 99.9997%이며, S3 복구 지점은 웹·사진·지도·API 배포 파일·접근 로그의 5개입니다.

## 3. 후속 검증과 운영 과제

**(3.1) v1·v2 모두 대상 응답이 4xx에 집중돼 정상 부하에서의 인프라 성능 비교는 미확보**

v1의 대상 응답은 **1,185건 중 4xx 1,175건**, v2는 **83건 모두 404**였습니다. v2의 DSQL 트랜잭션·DPU 표본은 확보되지 않았습니다. 다음 용량 검증의 대상은 **정상 요청 부하에서의 EC2 CPU·메모리 사용률, ALB 대상 응답 시간, DB 연결 수·처리량**입니다.

**근거:** CloudWatch의 v1 대상 응답 1,185건 중 4xx가 1,175건이고, v2 ALB 로그의 대상 응답 83건은 모두 404이며, 같은 날 DSQL 트랜잭션·DPU 지표에는 표본이 없습니다.

**(3.2) API 2대 → 1대 축소 후 장애 복구 수준은 미검증**

비교일에는 교체·장애 복구·백업 복원 시험 기록이 없습니다. v2의 교체 설정은 최소 정상 비율 **100%**, 최대 정상 비율 **200%**, 자동 롤백과 경보 연결을 사용합니다. API·NAT·DSQL Endpoint가 같은 가용 영역에 있어, **교체 중 정상 대상 유지와 장애 후 API·DB 접속 복귀 시간을 복구 기준으로 측정해야 합니다.**

온디맨드 백업은 운영자가 변경 전에 실행하고 완료를 확인하는 정책입니다. 복구 시험에는 보존 데이터 확인과 복원한 DB에 대한 API 재연결을 포함합니다.

**근거:** 조회한 ASG Instance Refresh 이력과 비교일의 AWS Backup 복원 작업은 비어 있으며, [교체 설정](../modules/compute/main.tf)은 정상 비율 100%·200%, [백업 정책](../madr/0010-aws-backup-management.md)은 새 백업 완료 후 변경과 복원된 DB의 접속 설정 갱신을 명시합니다.

**(3.3) v1 원본 로그 미확보로 v2와의 요청별 응답·오류 비교 제한**

v1은 과거 지표와 기존 분석 기록을 확보했습니다. **9월 18일의 ALB·CloudFront 원본 로그는 확보하지 못했습니다.** 요청별 응답 시간과 오류 발생 위치를 같은 기준으로 다시 분석하려면, 재구성 전에 비교 대상 날짜의 원본 로그와 집계 결과를 함께 보존해야 합니다.

**근거:** 현재 CloudWatch 로그 그룹은 v1 비교일 이후에 생성됐고, v1 CloudFront 로그 버킷 조회는 404를 반환해 해당 날짜의 원본 로그를 가져오지 못했습니다. [v1 로그 보존 기준과 비교 자료 보존 필요성](insight.md)
