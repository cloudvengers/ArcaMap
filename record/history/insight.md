## 3. Identify risks — 위험 식별

**(3.1) API 서버 2대 교체 중 ALB 정상 대상 수 0대 기록**

9월 15일 교체 정책은 최소 정상 비율 **0%**, 최대 용량 비율 **100%**였고, 자동 롤백과 경보 연결은 꺼져 있었습니다. **01:33:33**에 시작 템플릿 v2에 새 AMI가 반영됐으며, **01:33:46~01:33:48**에 기존 2대가 서비스에서 제외되고 새 2대의 시작 활동이 이어졌습니다. ALB 정상 대상 수의 **1분 최솟값은 01:34·01:35에 각각 0대, 01:36·01:37에 각각 2대**였습니다. **서버 2대 구성에서도 교체 중 정상 용량이 사라졌습니다. 축소 설계에는 상시 서버 대수와 별도로 교체 중 유지할 정상 용량이 필요합니다.** [근거: 운영 우수성 4.1](01-operational-excellence.md#41-api-배포의-정상-처리-용량-공백)

> **발생 원인:** [IaC 교체 정책 설정 미흡] Terraform으로 이미지 빌드와 서버 교체를 관리하면서 최소 정상 비율 0%·최대 용량 비율 100%를 적용해, 기존 API 서버 2대가 먼저 제외되고 새 서버 준비가 완료될 때까지 정상 대상 0대 발생

**(3.2) 서비스 경보 9개 자동 알림 미설정**

API·DB 서비스 경보 **9개**에는 알림 대상이 없고 알림 동작도 꺼져 있습니다. 정상 대상 부족 경보는 9월 15일 **01:38:43에 ALARM, 01:40:43에 OK**로 변경됐습니다. **감지 기능은 이미 있으므로, 직접 감시하는 운영 방식에 맞춰 기존 경보와 관련 지표를 통합 대시보드에 모으는 것이 우선입니다.** [근거: 운영 우수성 4.2](01-operational-excellence.md#42-서비스-경보의-감지와-전달)

> **운영 방식:** [SNS 미사용] 모니터링 시스템에서 서비스 상태와 경보를 직접 확인하고 있어 SNS 알림 대상은 의도적으로 미설정

**(3.3) CloudFront WAF 관리형 규칙 그룹 4개는 Count로 동작**

CloudFront WAF의 관리형 규칙 그룹 **4개**는 규칙 일치를 기록하는 Count로 동작합니다. **현재 규칙의 역할은 탐지·기록이며, 차단 전환 여부는 규칙별 오탐과 정상 요청 영향을 기준으로 판단할 대상입니다.** [근거: 보안 4.1](02-security.md#sec-f01)

**(3.4) API 요청을 받는 ALB에 WAF 미연결**

CloudFront의 WAF는 정적 콘텐츠 요청을 검사하지만, API 요청을 받는 ALB에는 WAF가 연결돼 있지 않습니다. **현재 CloudFront WAF의 검사 범위에는 API 진입점이 포함되지 않습니다. API 보호 범위는 정적 콘텐츠와 별도의 설계 대상입니다.** [근거: 보안 4.1](02-security.md#sec-f01)

**(3.5) IAM 사용자 1명에게 상시 관리자 권한 부여**

IAM 사용자 **1명**은 MFA가 등록돼 있으며 상시 `AdministratorAccess`를 보유합니다. **일상 작업에도 전체 관리자 권한이 적용돼, 계정 오용 시 영향 범위가 개별 서비스로 제한되지 않습니다.** [근거: 보안 4.3](02-security.md#sec-f03)

> **계정 환경:** [AWS Organizations 사용 불가] 계정 특성상 현재 사용 불가능으로 향후 랜딩존 구축 예정

**(3.6) RDS 백업 3일 보존·자동 스냅샷 4개, 집계 기간 내 백업 완료 8회**

RDS 자동 백업 보존 기간은 **3일**입니다. 공통 기간에 백업 시작 **9회**, 완료 **8회**가 기록됐고, 마지막 시작은 **9월 21일 23:55**로 완료 시각은 집계 기간 밖입니다. 구성 확인 시점에는 **9월 18~21일 생성된 암호화 자동 스냅샷 4개**가 사용 가능했습니다. 복원 후 업무 재개 시험 기록은 없습니다. **DB 이전에 활용할 백업은 확보돼 있으며, 복원된 데이터와 API 연결의 정상 여부가 실제 이전 가능성을 판단할 기준입니다.** [근거: 신뢰성 4.3](03-reliability.md#43-rds-자동-백업의-복원-범위와-미검증된-복구-목표)

**(3.7) 웹·지도·API 배포 파일의 버전 관리 미설정**

웹·지도·API 배포 파일에는 버전 관리가 없으며, 원본에서 다시 만드는 절차는 검토 자료에서 확인되지 않았습니다. **파일별 이전 버전이나 재생성 경로가 확보돼야 인프라 교체 실패 시 콘텐츠와 API를 되돌릴 수 있습니다.** [근거: 신뢰성 4.3](03-reliability.md#43-rds-자동-백업의-복원-범위와-미검증된-복구-목표)

## 4. Understand risks — 위험 이해

**최우선 방향은 서비스 인프라 전면 교체·축소입니다.** RDS와 NAT 유지비 **69.79%**, API 평균 CPU **0.56%·0.64%**, ASG **2대 유지**를 근거로 DB 구성·외부 통신 경로·API 최소 용량을 재검토합니다.

**(4.1) IAM 역할 생성 직후 시작 활동 3건 실패, 자동 재시도로 EC2 2대 기동**

9월 14일 **01:51:18**에 Auto Scaling 서비스 연결 역할이 생성되고, **01:51:19**에 ASG가 생성됐습니다. **01:51:22**부터 역할 인수가 거부돼 **01:51~01:52**의 인스턴스 시작 활동 **3건**이 실패했습니다. 이후 자동 재시도로 **01:52:22에 2c**, **01:54:20에 2a** 인스턴스가 시작됐으며, 두 대 모두 EC2 상태 검사 기준 **InService·Healthy**로 확인됐습니다. **정상 신뢰·관리 정책과 자동 재시도 성공은 지속적인 권한 누락보다 역할 생성 직후의 전파 지연을 뒷받침합니다.** [근거: ASG 역할 사용 거부 기록](/root/protomaps/docs/troubleshooting.md:91)

> **발생 원인:** [IAM 전파 지연 추정] 역할의 신뢰 정책과 관리 정책은 정상이었으나 생성 직후 서비스 반영에 시간이 필요해 초기 역할 인수 실패 후 자동 재시도로 인스턴스 2대 기동

> **Terraform 영향:** [자동 복구 후 교체 표시 잔존] EC2 2대 정상화 이후에도 ASG에 tainted 표시가 남아 실제 서비스 상태와 Terraform 교체 계획 간 불일치 발생

**(4.2) 인스턴스 기동 후 API 준비 지연, ALB 502·503 총 307건**

9월 14일 **01:52~01:59**의 두 인스턴스 시작 활동은 성공했지만, API 관련 첫 시스템 기록은 **22:34**, 첫 헬스 체크 HTTP 200은 **22:40**에 나타났습니다. ALB 접근 로그에는 **502 응답 303건(01:55~22:35)**, **503 응답 4건(01:27~01:48)**이 기록됐습니다. **EC2 기동 성공과 API 서비스 준비 완료는 서로 다른 상태입니다. 축소·재구성의 가용성 판단에는 ALB 정상 판정·API 응답·DB 연결 결과가 필요합니다.** API 준비 지연의 앱 내부 원인은 미확인입니다. ## 5. Determine prescriptive solutions — 해결 방안 결정

**(5.1) 서비스 인프라 전면 축소·재구성**

약 일주일간의 운영 관측과 비용 분석을 바탕으로, **운영 비용 절감과 서버 관리·운영 역량 향상**을 목적에 둔 인프라로 전면 재구성합니다. API 평균 CPU **0.56%·0.64%**, RDS 평균 CPU **5.23%**, 7일 추정 사용료 **79.02달러** 중 RDS와 NAT 유지비 **69.79%**를 근거로 상시 자원 수와 유지 비용을 줄입니다. [근거: 비용 최적화 4.1](05-cost-optimization.md#billing-findings), [4.2](05-cost-optimization.md#capacity-findings)

설계 기준은 **서비스 목적과 운영 요구사항(Workload Requirements)**입니다. API EC2 상시 1대와 Aurora DSQL 서울 리전·단일 리전 구성에서 **SLO(Service Level Objective, 서비스 수준 목표)의 범위는 AWS 인프라로 한정하며, SLO 목표값과 장애 한 번의 허용 중단 시간은 재구성 후 운영 데이터와 복구 시험 결과를 확보한 뒤 결정합니다.** 가용성·중단 시간·복구 시간의 측정 기준과 수집 방법을 먼저 정하고, ASG 자동 교체 후 ALB 정상 대상 복귀까지의 시간을 확인합니다. 자동 복구와 수동 대응이 필요한 장애를 구분하고, 운영 결과·장애 영향·대응 여건·운영 비용을 함께 고려해 기준을 정합니다. 백업·복원은 5.7의 업데이트 직전 버전 보존 및 복원 검증 기준을 따릅니다. [SLO·허용 중단 시간 결정 시점](../../v2/record/slo-after-operational-data.md)

| 구성 요소 | 재구성 방향 | 선택 근거 |
|---|---|---|
| API 서버 | EC2 상시 1대 | 낮은 관측 CPU 사용률을 반영한 용량 축소와 서버 관리·운영 경험 확보 |
| 데이터베이스 | Aurora DSQL — 서울 리전(`ap-northeast-2`), 단일 리전 구성 | 사용량 기반 과금으로 상시 DB 인스턴스 비용 회피 |
| ASG·ALB 등 기존 구성 | 유지 | 주요 변경 범위는 EC2 상시 대수와 DB 구성 |

기존 7일 추정 사용료에서 RDS는 **35.33달러(전체의 44.71%)**였으며, **Multi-AZ 실행료 34.10달러**가 포함됐습니다. 이를 근거로 DB 활동과 저장량에 따라 과금하는 Aurora DSQL을 선택합니다. 단일 리전에서도 여러 AZ에 걸친 고가용성을 제공하며, 실제 절감액은 전환 후 사용량에 따라 달라집니다. [DB 선택 결정·공식 문서·이점과 제약](../../v2/record/database-aurora-dsql.md)

> **운영 목적:** [서버 관리·운영 역량 향상] API 서버는 EC2를 사용해 서버 구성과 배포·모니터링·장애 대응을 직접 운영하는 경험 확보

> **구성 방향:** [API EC2 1대·Aurora DSQL 단일 리전] API 상시 용량과 DB 인스턴스 유지 비용을 줄입니다. 인프라 SLO 목표값과 허용 중단 시간은 재구성 후 운영 데이터·복구 시험 결과 확보 뒤 결정합니다. 백업은 업데이트 직전 버전을 8일 보존하며, 복원 검증은 5.7의 기준을 따릅니다.

**축소 효과는 재구성 전후의 동일 기간 비용과 API 응답·오류·메모리 사용량으로 비교합니다.** 기존 RDS와 NAT 유지비 비중 69.79%는 비용 구조의 관측값입니다.

**(5.2) API 교체 중 정상 용량 유지**

ASG Instance Refresh의 교체 순서를 새 서버 준비 후 기존 서버 제외로 변경합니다. ASG의 최소·목표 용량은 **1대**를 기준으로 조정합니다.

기존 [교체 설정](../../terraform/modules/compute/main.tf#L67)은 최소 정상 비율 **0%**, 최대 용량 비율 **100%**입니다. 다음 변경안은 상시 EC2 1대를 유지하면서 교체 중에만 새 서버 1대를 추가하는 구성입니다.

| 설정 | 기존 | 변경안 | 목표 용량 1대 기준 의미 |
|---|---|---|---|
| `min_healthy_percentage` | 0 | 100 | 교체 중 정상 용량 1대 유지 |
| `max_healthy_percentage` | 100 | 200 | 교체 중 정상 상태이거나 기동 중인 서버를 합쳐 최대 2대 허용 |

비율의 기준은 목표 용량인 `desired capacity`입니다. 최소 정상 비율 100%에서는 새 인스턴스를 먼저 생성하고 정상 상태와 워밍업 시간을 확인하며 교체합니다. [AWS 공식 문서 — Instance Refresh 동작](https://docs.aws.amazon.com/autoscaling/ec2/userguide/instance-refresh-overview.html), [교체 비율 정의](https://docs.aws.amazon.com/sdk-for-ruby/v3/api/Aws/AutoScaling/Types/RefreshPreferences.html)

적용 조건은 추가 인스턴스를 실행할 자원 여유와 ALB 상태 검사이며, 검증 기준은 교체 중 정상 대상 수 유지입니다.

**(5.3) CloudWatch Agent 메모리 지표 수집 추가**

Agent는 이미지 빌드 중 설치·활성화되고 API 인스턴스 부팅 시 실행되도록 구성돼 있습니다. 기존 IaC 수집 설정은 `journald` 로그만 포함하며 메모리 지표용 `metrics` 설정은 없습니다. [Agent 설치 코드](/root/protomaps/terraform/modules/image-builder/main.tf:67), [인스턴스 시작 코드](/root/protomaps/terraform/modules/compute/main.tf:36), [수집 설정](/root/protomaps/terraform/env/was/main.tf:45)

기존 `cloudwatch_agent_config`의 `metrics.metrics_collected.mem`에 메모리 사용률과 사용 가능한 메모리 수집을 추가합니다. EC2 1대의 CPU·메모리 사용량과 요청 집중 시간대의 API 응답·오류를 축소한 용량의 적정성 판단에 활용합니다.

**(5.4) CloudWatch 통합 대시보드 구성**

기존 지표·경보와 Logs Insights 조회 결과를 하나의 대시보드에 모아 같은 시간대의 상태를 비교합니다. ASG·ALB 모니터링은 유지하고, 인스턴스·정상 대상 수 경보는 EC2 1대 기준으로 조정합니다. DB 관련 지표·경보는 Aurora DSQL에서 제공하는 항목에 맞춥니다. [AWS 공식 문서 — CloudWatch 대시보드](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Dashboards.html), [대시보드 위젯](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/create-and-work-with-widgets.html)

| 구분 | 함께 확인할 내용 |
|---|---|
| 서비스 상태 | EC2 1대·Aurora DSQL에 맞춘 경보, ALB 정상 대상 수 |
| 요청 상태 | API 요청량, ALB·API의 HTTP 오류, 응답 시간 |
| 자원 상태 | ASG 인스턴스 수, EC2 1대의 CPU·메모리, Aurora DSQL의 DPU 사용량·저장량 등 제공 가능한 지표 |
| 원인 확인 | 같은 시간대의 ALB·시스템·DB 주요 오류 로그 |

대시보드는 동일한 조회 시간대, 실제 수집 중인 로그 그룹, EC2 메모리 지표(5.3)를 기준으로 구성합니다. 정의는 Terraform으로 관리합니다.

**CloudWatch Logs 로그 그룹의 보존 기간은 7일로 설정합니다.** 기존 수집 항목을 대상으로 로그 통계는 하루 단위로 집계해 최근 7일을 조회합니다. 지표도 하루 단위 통계로 조회하되, 보존 기간은 AWS 기본 정책(1분 단위 15일·5분 단위 63일·1시간 단위 455일)을 따릅니다. [로그 보존 기간 결정](../../v2/record/cloudwatch-logs-retention.md)

향후 S3의 CloudFront 로그를 Athena로 조회해 기존 지표와 함께 분석하거나 AWS 외부 데이터를 통합할 경우 Grafana 확장을 검토합니다. 데이터 소스 연결·접근 권한·운영 비용을 기준으로 도입 여부를 결정합니다. [AWS 공식 문서 — Grafana의 CloudWatch 연결](https://docs.aws.amazon.com/grafana/latest/userguide/using-amazon-cloudwatch-in-AMG.html), [Grafana의 Athena 데이터 소스](https://docs.aws.amazon.com/grafana/latest/userguide/Athena-using-the-data-source.html)

**(5.5) AMI 기반 불변 배포에 CI/CD 도입**

기존 **AMI 기반 불변 배포(Immutable Deployment)**를 유지하고, CI/CD로 테스트·배포 파일 생성·Terraform 실행을 자동화합니다. 기존 Image Builder와 ASG Instance Refresh 구성을 활용해 반복적인 배포 작업을 줄입니다.

현재 Terraform은 미리 생성한 배포 파일을 입력으로 받아 S3 업로드부터 AMI 빌드·서버 교체까지 연결합니다. 이 구성을 바탕으로 코드 변경부터 배포까지 하나의 파이프라인으로 구성합니다. [배포 파일 업로드](../../terraform/env/was/deployment.tf), [AMI 생성](../../terraform/modules/image-builder/main.tf), [서버 교체 설정](../../terraform/modules/compute/main.tf)

| 구분 | 구성 방향 |
|---|---|
| 테스트·배포 파일 생성 | CI/CD 파이프라인에서 애플리케이션 테스트와 배포 파일 생성 자동화 |
| AMI 배포 | 파이프라인의 Terraform 실행으로 기존 S3 업로드·Image Builder 구성 활용 |
| 운영 서버 교체 | ASG Instance Refresh의 롤링 교체 유지 및 5.2의 정상 용량 유지 정책 적용 |

**(5.6) WAF 적용 범위 확대와 규칙·비용 조정**

CloudFront WAF의 Anti-DDoS 관리형 규칙 그룹을 제외해 추가 비용을 줄이고, API 요청을 받는 ALB에도 WAF를 적용합니다. 유지할 관리형 규칙에는 차단을 적용하고, 정상 요청에 필요한 예외와 요청량 제한 기준을 설정합니다.

현재 CloudFront의 관리형 규칙 그룹 **4개**는 모두 Count로 설정돼 있으며, ALB에는 WAF가 연결돼 있지 않습니다. 7일 WAF 사용료 **6.06달러** 중 Anti-DDoS 기능 유지료는 **4.18달러(68.90%)**입니다. [근거: 보안 4.1](02-security.md#sec-f01), [비용 최적화 4.5](05-cost-optimization.md#45-waf-검사-비용과-가격-모델의-선택-조건)

| 구분 | 구성 방향 |
|---|---|
| Anti-DDoS | 관리형 규칙 그룹 제외로 해당 추가 비용 절감 |
| 기존 관리형 규칙 | IP 평판·일반 웹 공격·알려진 악성 입력 규칙 그룹 유지 및 차단 적용 |
| API 보호 | ALB에 WAF를 연결하고 API 요청에 맞는 차단 규칙과 예외 설정 |
| 요청량 제한 | 정상 요청량과 경로별 처리 부담을 기준으로 제한 규칙 설정 |

**(5.7) 모든 백업 대상의 업데이트 직전 버전 보존**

**모든 백업 대상은 정기 백업 대신 업데이트 시 변경 직전의 이전 버전만 보존하며, 이전 보존 기간은 8일로 합니다.** 변경이 없으면 새 백업을 만들지 않으며 잔여물은 전부 삭제합니다(불필요한 저장으로 인한 금액 방지).

| 문서에서 확인한 대상 | 업데이트 시 보존할 내용 |
|---|---|
| DB | 데이터·스키마 변경 직전 상태 |
| AMI | 이전 정상 AMI |
| 사진 파일 | 변경 직전 버전 |
| 웹 파일 | 변경 직전 버전 |
| 지도 파일 | 변경 직전 버전 |
| API 배포 파일 | 변경 직전 버전 |

위 목록에 한정하지 않고 모든 백업 대상에 같은 기준을 적용합니다. 업데이트 절차에 이전 버전 보존을 포함하고, 보존 중인 버전을 복원 대상으로 삼습니다. [백업 방식 결정]

복원 시험은 운영 데이터와 분리된 환경에서 수행합니다. 복원된 데이터와 API·DB 연결을 확인하고 복원 소요 시간을 기록하며, 콘텐츠는 보존한 이전 버전의 복원 경로를 확인합니다. [신뢰성 문서의 복원 검증 기준](03-reliability.md#43-rds-자동-백업의-복원-범위와-미검증된-복구-목표)
