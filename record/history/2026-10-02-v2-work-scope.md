# ArcaMap v2 작업 범위와 협업 기준

- 기록일: 2026-10-02 (KST)
- 작성자: 코디네이터
- 현재 단계: 작업 범위 협의 및 기록
- 이 문서는 사용자와 합의한 사항과 아직 확정하지 않은 분담 초안을 구분합니다.

## 1. 작업 목표와 기준

현재 코드는 이전 버전입니다. `/root/v2/madr`의 아키텍처 결정을 구현하도록 Terraform과 필요한 애플리케이션 코드를 수정하고, 에이전트의 사전 검증과 사용자·코디네이터의 2차 검증을 거쳐 ArcaMap v2를 AWS에 신규 배포합니다.

구현 기준은 사용자 지시와 MADR입니다. 기존 코드·README·운영 기록은 구조와 의존성, 과거 운영 배경을 파악하는 자료로 사용합니다. 기존 코드의 구성을 그대로 유지하는 것이 목표는 아닙니다.

### 기존 리소스와 신규 구성의 구분 — 사용자 정정 반영

**기존 S3 중 재사용 대상은 지도 버킷입니다. 기존 S3 전체를 재사용하는 것으로 해석하지 않습니다.**

| 대상 | 작업 기준 |
| --- | --- |
| 기존 지도 S3 버킷 | 재사용합니다. MADR에 따른 버전 관리·수명주기·접근 정책 등의 변경 범위를 검토합니다. |
| 기존 도메인 | 재사용합니다. v2 서비스와의 DNS 연결을 구성합니다. |
| 웹 정적 파일·사진·CloudFront 접근 로그·API 배포용 S3 버킷 | 지도 버킷 재사용과 구분하여 MADR에 따른 신규 구성 대상으로 다룹니다. 기존 버킷을 재사용한다고 전제하지 않습니다. |
| v2 서비스 인프라 | 신규 배포를 전제로 Terraform을 구성합니다. 실행 중인 이전 서비스 인프라의 이전 작업으로 다루지 않습니다. |
| ACM 인증서·DNS 관리 권한 | 기존 구성과 사용 가능 여부가 아직 확인되지 않았습니다. 확인 후 필요한 작업 범위를 정합니다. |

이 구분은 대화에서 확인한 사용자 설명을 기준으로 합니다. AWS 리소스의 실제 목록을 조회해 검증한 상태는 아닙니다.

## 2. 작업 경로

| 경로 | 역할 |
| --- | --- |
| `/root/v2` | 작업 기준 경로 |
| `/root/v2/madr` | v2 설계 결정과 구현 기준 |
| `/root/v2/modules` | Terraform 리소스 모듈 수정 |
| `/root/v2/env` | Terraform 루트 구성·모듈 연결 수정 및 필요한 환경 추가 |
| `/root/v2/app` | 변경이 필요한 사항을 모아 담당 범위를 별도로 정할 애플리케이션·데이터·배포 코드 |
| `/root/v2/record/history` | 합의한 작업 기준과 각 에이전트의 개인 작업 기록 |

팀 전체 진행·질문·결정·조율 기록은 Slack의 Ki 워크스페이스 [`#arcamap`](https://ki-rqi2757.slack.com/archives/C0C5U4S1NUX) 채널을 사용합니다.

## 3. 역할과 실행 방식 — 합의 사항

### 사용자와 코디네이터

- 사용자와 코디네이터가 작업 범위와 담당 경계를 함께 정합니다.
- 사용자는 에이전트의 공통 작업 워크플로우를 정합니다.
- MADR에 따른 구체적인 IaC 수정 사항·수정 파일·담당 범위·완료 조건은 코디네이터가 정리해 에이전트에게 지시합니다.
- 코디네이터는 사용자와 합의한 범위 안에서 MADR와 공통 작업 워크플로우를 반영해 작업을 배정합니다.
- 코디네이터는 중앙에서 진행 상황과 의존 관계를 관리하고, 질문·결정 필요 사항·중요 결과를 종합해 사용자에게 보고합니다.
- 사용자와 논의한 결정은 담당 에이전트에게 전달합니다.
- 구현 수정과 보완은 담당 에이전트에게 배정합니다. 코디네이터는 조율·기록·검토를 담당합니다.
- 코디네이터는 분담안을 먼저 사용자에게 보고하고, 확정되거나 기록을 지시받은 내용을 문서에 반영합니다.
- 에이전트 작업의 2차 검증과 통합 검증은 사용자와 코디네이터가 함께 진행합니다. 별도의 통합 검증 에이전트는 두지 않습니다.

### 작업 에이전트

- Orca CLI 오케스트레이션으로 실행합니다.
- 지정 모델은 `gpt-6.1-sol`, 추론 강도는 `xhigh`입니다.
- 실행 시 실제 적용된 모델과 추론 강도를 확인합니다.
- 에이전트별 수정 대상과 인계할 입력·출력을 정한 뒤 작업을 시작합니다.
- 현재 작업 에이전트의 범위는 IaC 수정·본인 작업의 사전 검증·개인 history 작성입니다.
- 작업은 병렬로 진행합니다. 독립적인 수정은 동시에 수행하고, 선행 결과가 필요한 부분만 코디네이터가 순서를 조율합니다.
- 같은 파일은 한 명의 담당자만 수정합니다. 다른 담당 파일의 변경이 필요하면 코디네이터를 통해 해당 담당자에게 요청합니다.
- 서로 사용할 입력·출력의 이름·자료형·전달 방식을 맞추고, 변경이 생기면 코디네이터가 관련 담당자에게 전달합니다.
- 선행 결과를 기다리는 동안 진행할 수 있는 나머지 수정·검증·기록 작업을 계속합니다.
- 각 에이전트는 자신의 작업 기록 파일을 `/root/v2/record/history`에 생성하고 진행에 따라 갱신합니다.

### 에이전트 공통 작업 절차 — 사용자 지시

1. **전역 지침 전체 확인:** 작업 시작 전에 전역 지침을 첫 줄부터 끝 줄까지 읽고 내용을 파악합니다.
2. **계획 생성 후 진행:** 모든 작업은 `update_plan`을 생성한 뒤 진행합니다. 전역 지침에 따라 원자적 작업 대상을 기준으로 검색·수정·생성·검증·보고 범위를 구분하고, 계획을 보고한 뒤 승인된 계획에 따라 수행합니다.
3. **수정 직전 스킬·MCP 확인:** 코드 수정 직전에 반드시 관련 스킬을 읽고 MCP로 수정에 필요한 근거를 확인한 뒤 수정합니다. 확인 없이 임의로 코드를 수정하지 않습니다. MCP에서 확인할 수 없는 사항은 전역 지침에 따라 공식 문서를 추가로 확인합니다.
4. **공식 문서 출처 기록:** 작업 문서와 개인 history에 참고한 공식 문서의 링크를 기재합니다. 수정 내용·판단 근거와 연결해 어떤 내용을 참고했는지 확인할 수 있도록 기록합니다.

## 4. Terraform 병렬 작업 분담 초안 — 세부 범위 미확정

IaC 담당 6명의 병렬 분담안입니다. 번호는 담당자를 구분하며 실행 순서를 뜻하지 않습니다. 에이전트별 구체적인 수정 지시사항, 최종 수정 파일 목록과 완료 조건은 코디네이터가 MADR를 기준으로 작성합니다. 담당 경계와 조율 사항은 사용자에게 보고하고 확정한 내용을 반영합니다. 실제 AWS 배포 순서는 별도로 정합니다.

| 담당 | 역할 | 주요 수정 범위 | 주요 인계 내용 |
| --- | --- | --- | --- |
| 1 | 네트워크·보안 | `modules/network`, `modules/security`, `env/network` | 서브넷·NAT, API·빌드·DSQL Endpoint 보안그룹, 후속 구성에서 사용할 출력값 |
| 2 | 데이터베이스 | `modules/database`, `env/database` 중 `monitoring.tf` 외 파일 | DSQL 클러스터·Endpoint, 접속정보, API 연결에 필요한 입력값 |
| 3 | 저장소·콘텐츠 | `modules/s3-bucket`, `modules/cloudfront`, `env/frontend` | 공통 S3 모듈 입력·출력, 기존 지도 버킷 연결, 콘텐츠 버킷·캐시·보안 헤더 |
| 4 | API·이미지 | `modules/compute`, `modules/image-builder`, 필요한 `modules/alb`, `env/api` 중 `monitoring.tf` 외 파일 | DSQL 인증·접속 설정, IAM, AMI 빌드, ASG·교체 설정 |
| 5 | 관측·알림 | `modules/cloudwatch-alarm`, `modules/cloudwatch-log-group`, `modules/cloudwatch-dashboard`, `env/monitoring`, `env/database/monitoring.tf`, `env/api/monitoring.tf` | API·DSQL 경보, SNS 상태 알림, 로그·통합 대시보드 |
| 6 | 백업 | 신규 `env/backup`과 필요한 백업 구성 | 공통 백업 볼트·KMS·백업 및 복원 권한·DSQL 보호 설정 |

`app`의 변경은 이번 IaC 담당 범위에 포함하지 않습니다. DSQL 접속·스키마·적재·배포 코드 등의 변경 필요 사항을 모아 사용자에게 보고한 뒤 별도로 담당 범위를 정합니다.

### 분담 확정 전에 정할 경계

- **파일 담당:** DB·API의 `monitoring.tf`는 관측 담당자가 수정하고, 같은 루트의 `variables.tf`·`outputs.tf`는 DB·API 담당자가 각각 수정하는 안입니다. 관측 담당자가 변수·출력 변경을 필요로 하면 코디네이터를 통해 요청합니다.
- **공통 모듈:** S3·경보 모듈의 입력·출력을 변경하면 해당 모듈을 호출하는 루트의 후속 변경도 함께 추적합니다.
- **앱 연계:** 별도 앱 작업에 필요한 환경변수·파일 형식·DB 역할과 초기화 조건을 IaC 담당자가 명시합니다.
- **초기 배포 선행 조건:** DSQL·Endpoint, IAM 역할, DB 역할 매핑·스키마·데이터 초기화가 AMI의 DB 연결 검사보다 먼저 준비되도록 구성 책임을 나눕니다.
- **SNS 참조 방향:** SNS 생성 위치와 서비스 경보·대시보드의 참조 방향을 정해 루트 간 순환 의존을 피합니다.
- **기존 기반 연결:** 지도 버킷·도메인 재사용을 전제로 인증서·DNS 권한의 확인 결과에 따라 담당 범위를 정합니다.

## 5. 기록·완료 보고·검토 기준 — 합의 사항

### 개인 history

각 에이전트는 다른 에이전트의 기록을 덮어쓰지 않도록 별도 파일을 사용합니다. 파일명은 작업 배정 시 지정합니다.

기록에는 다음 내용을 남깁니다.

1. 배정받은 범위와 적용한 MADR.
2. 진행 내용과 실제 수정한 파일.
3. 입력·출력·선행 조건의 변경 및 후속 작업에 미치는 영향.
4. 본인이 실행한 사전 검증의 명령·대상·결과, 실행하지 못한 검증 및 이유.
5. 질문·결정 사항·미해결 문제와 다음 담당자에게 전달할 내용.
6. 코드 수정 전에 확인한 스킬·MCP의 내용과 참고한 공식 문서 링크.

### 사전 검증과 2차 검증

1. **에이전트 사전 검증:** 각 에이전트는 자신이 수정한 IaC를 검증하고, 결과와 미검증 사항을 개인 history에 남깁니다. 미실행 검증을 통과한 것으로 보고하지 않습니다.
2. **사용자·코디네이터 2차 검증:** 코디네이터가 작업 기록·문서·실제 변경 코드·사전 검증 결과를 검토하고, 사용자와 함께 전체 연결과 MADR 충족 여부를 검증합니다.
3. **보완:** 문제가 발견되면 담당 에이전트가 수정·재검증하고 결과를 기록합니다. 사용자와 코디네이터가 보완 결과를 다시 확인합니다.

## 6. 최종 배포 — 합의 사항

- 에이전트의 작업 범위는 배정된 수정·검증·기록까지입니다. 에이전트가 최종 배포를 실행하지 않습니다.
- 모든 에이전트의 작업·사전 검증·필요한 보완과 사용자·코디네이터의 2차 검증이 끝난 뒤 최종 배포를 진행합니다.
- 최종 배포는 사용자와 코디네이터가 함께 진행합니다.

## 7. 현재 진행 상태

- 프로젝트 목적·폴더 구성과 MADR 0001~0010의 내용을 확인했습니다.
- Terraform의 주요 루트·모듈 연결을 확인하고 IaC 담당 6명의 병렬 작업 분담 초안을 작성했습니다.
- 지도 버킷과 도메인의 재사용 기준을 사용자 정정에 따라 명시했습니다.
- 에이전트의 사전 검증, 사용자·코디네이터의 2차 검증, Slack `#arcamap`을 통한 팀 공동 기록 방식을 반영했습니다.
- Slack MCP로 `#arcamap` 채널에 시험 메시지를 게시했고 사용자가 정상 확인했습니다.
